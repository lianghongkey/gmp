# 使用流程

本文讲怎么把板子跑起来生成文字：一条命令的最短路径、这条命令替你做了哪些事、每步要多久、
结果不对时先看什么。环境准备在 [`setup.md`](setup.md)，手上没有板子时看
[`simulation.md`](simulation.md)。

**文档模式**：操作步骤。

## 一条命令

板子上电、线缆与网线都插好，直接跑：

```bash
python host/soc_generate.py "今天天气不错，我们去"
python host/soc_generate.py --chat "请用一句话介绍一下你自己。"
python host/soc_generate.py --file prompt.txt --max-new 32 -v
```

第一次跑（板子刚上电、里面什么都没有）它会自己烧 bitstream、灌权重，两分钟上下；之后每次
再跑只花几秒钟把板子查一遍，然后直接开始生成。生成过程是逐 token 打印的。

`--chat` 按 Qwen3 的对话模板包一层，不加就是纯续写。

## 跑起来是什么样

2026-09-08 的一趟实录。板上已经烧着这份 bitstream，这一趟把 762 MiB 权重整份重灌了一遍：

```text
$ python host/soc_generate.py --load-weights --chat "请用一句话介绍一下你自己。"
── Qwen3 0.6B Instruct：prompt 18 个 token（纯 Python BPE）──
    计划：不满 64，逐个喂 18 个（decode n_seq = 1..18），然后最多生成 111 个（上下文 128）；停在 [151643, 151645]
── 板子 ──
    板上认出这颗 SoC
    DDR 校准完成
── 灌整份权重（762 MiB，约 1 分钟）──
      … 158 MiB（17.35 MB/s，还要约 1 分钟）
      …（每 64 MiB 报一行）
      … 762 MiB（17.33 MB/s，还要约 0 分钟）
    权重 761.7 MiB 灌完，0.7 分钟
    权重抽查 16 处一致
    清零：KV 每层前 128 格 × 56 块 + 中间张量 8 段，共 14.0 MiB，1 s
```

## 这条命令做的六件事

### 一、开跑前查一遍，不对的自己修

开跑前按阶梯查一遍，哪一级没过就当场修，修不了就停：

| 查什么 | 不对时怎么办 |
| - | - |
| 网口的链路开得起来 | 报权限不够就去 `setup.md` 的“权限”一节授一次；网口没 up、网线没插、SFP 模块没插紧，软件修不了，停 |
| 板上烧的是这颗 SoC（STAT 读到魔数 SOC1） | 认不出来就经线缆烧 `--bit` 那份 |
| DDR 两个通道都校准完 | 刚烧完要等，最多 30 秒 |
| 抽查 16 处权重与 `data/weights.npz` 一致 | 不一致就整份重灌 |

`--no-auto` 只诊断不动手，`--check-only` 查完就退出。

### 二、烧 bitstream

缺省烧 `prebuilt/bit/top_eth.bit`，走包内的 pyjtag，14 MB 约 13 秒，不需要 Vivado。
`--program` 是不管板上现在是什么都先烧一遍。

线缆只做这一件事。发布的 bitstream 上没有 JTAG⇆AXI 桥，读写一律走网口，所以烧完之后脚本会
回到网口重新开链路 —— 收发两侧要重新对齐，这几秒钟里开不起来是正常的，它会重试。

重烧会复位 DDR3 控制器，但十几秒的重烧之后 DDR3 里的数据还在，实测烧完抽查仍然一致，所以
烧完照样先抽查，以抽查结果为准。

### 三、灌权重

权重共 762 MiB，经网口写进片上，再由片上互联搬进 DDR3，实测约 10 MB/s，一分多钟。灌完再抽查一次。

只要板子不掉电、不重灌别的东西，权重一直在 DRAM 里，后面每次跑都跳过这一步。`--load-weights`
是不抽查直接重灌。

### 四、清残留

这一趟会碰到的 DRAM 区域里，输入没有覆盖到的部分要清零：KV cache 每层前 128 格乘 56 块，加上
中间张量的 8 段，共 14 MiB，一秒钟。上一趟留下的残留会被读进来影响结果。`--no-zero` 跳过。

### 五、把 prompt 喂进去

板上那份程序编好了两条路：

* **prefill** 一次处理 64 个 token，prompt 到 64 个及以上时走它，一轮 1.10 秒。
* **decode** 一次处理一个 token，一步 0.24 秒。prompt 里 prefill 处理不完的那些就靠它逐个喂
  （不满 64 个的 prompt 整段都这么喂，不能补零凑数）。

prompt 加生成一共最多 128 个 token，这是这份产物的上限。

### 六、生成

每步取片上算出的那个 token，接着喂回去，直到遇到结束符或到 `--max-new`。`--show-special`
把控制 token 也打出来，`--no-stop` 遇到结束符也不停。

分词用 `data/tokenizer.json.gz` 里的词表：编码走包内的纯 Python BPE，解码按 GPT-2 的
byte-level 表还原。手上有 Qwen3-0.6B 的 GGUF 时，`--vocab <那份 gguf>` 会把编码交给
llama.cpp 的 `llama-tokenize`，两条路径在常规中英文上给出同一串 token。

## 结果不对时

| 现象 | 先看这个 |
| - | - |
| 多数趟都对，偶尔一趟从某个 token 起走偏 | 原样再跑一趟，多半就对了。板子连续上电大半天之后这种零星数值错误会变密，断电再上电能压下去。先看板子上电多久了，不要急着怪到精度或者主机那一侧 |
| 生成的第一个 token 就不对 | 权重没灌对：跑 `--check-only`，抽查不过就整份重灌 |
| 每一步都超时 | 多半没烧 bitstream，或者烧错了那一份；`-v` 看每轮的状态快照 |
| 一开始就说链路开不起来 | 网口没 up（`ip link set <网口名> up`）、网线接了交换机而不是直连、SFP 模块没插紧；主机上不止一块网口时它会让你用 `--nic` 指一块 |
| 灌权重特别慢（1 MB/s 这个量级） | 网口协商到了百兆，或者中间经了交换机 |
| 命令卡住不动 | 别按第二次 Ctrl-C。第一次只是让它跑完当前这步就停；正在烧录时硬打断会把线缆卡在写得进、读不出的状态，只能把线缆拔下来重插 |

`--dry-run` 只分词、只算计划，不碰板子，用来把主机侧和板子问题分开。
