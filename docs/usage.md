# 使用流程

本文讲怎么把板子跑起来生成文字：一条命令的最短路径、这条命令替你做了哪些事、每步要多久、
结果不对时先看什么。环境准备在 [`setup.md`](setup.md)，手上没有板子时看
[`simulation.md`](simulation.md)。

**文档模式**：操作步骤。

## 一条命令

板子上电、线缆插好，直接跑：

```bash
python host/soc_generate.py "今天天气不错，我们去"
python host/soc_generate.py --chat "请用一句话介绍一下你自己。"
python host/soc_generate.py --file prompt.txt --max-new 32 -v
```

第一次跑（板子刚上电、里面什么都没有）它会自己烧 bitstream、灌权重，二十来分钟；之后每次
再跑只花几秒钟把板子查一遍，然后直接开始生成。生成过程是逐 token 打印的。

`--chat` 按 Qwen3 的对话模板包一层，不加就是纯续写。

## 跑起来是什么样

2026-09-04 的一趟实录。板上已经烧着这份 bitstream，但断过一次电，DDR3 里的权重没了，
所以这一趟把 604 MiB 整份重灌了一遍：

## 这条命令做的六件事

### 一、开跑前查一遍，不对的自己修

开跑前按阶梯查一遍，哪一级没过就当场修，修不了就停：

| 查什么 | 不对时怎么办 |
| - | - |
| 线缆打得开 | 报 `Resource busy` 是别的进程占着，杀掉残留的 `hw_server` 再来 |
| 板子是 xc7k480t | 读到全 1 或全 0 是板子没上电、排线松，软件修不了，停 |
| 板上烧的是这颗 SoC | 认不出来就烧 `--bit` 那份 |
| 读写通路一致 | 对不上同样重烧 |
| DDR 两个通道都校准完 | 刚烧完要等，最多 30 秒 |
| 抽查 16 处权重与 `data/weights.npz` 一致 | 不一致就整份重灌（重烧过必然不一致） |

`--no-auto` 只诊断不动手，`--check-only` 查完就退出。

### 二、烧 bitstream

缺省烧 `prebuilt/bit/top_jtag_p3.bit`（50 MHz）。走 pyjtag 自己的烧录，14 MB 约 13 秒；DONE
没拉起来时改用 Vivado（`--prog-tool vivado`）。`--program` 是不管板上现在是什么都先烧一遍。

要跑快的那份：

```bash
python host/soc_generate.py --program --bit prebuilt/bit/top_jtag_c66n.bit "今天天气不错，我们去"
```

重烧会复位 DDR3 控制器。实测十几秒的重烧之后权重抽查仍然一致（这十几秒里 DDR3 的数据还在），
所以烧完照样先抽查，以抽查结果为准。

### 三、灌权重

权重共 604 MiB，经 JTAG 写进 DDR3，按线缆实测 0.55 MB/s 算约 18 分钟。灌完再抽查一次。

只要板子不掉电、不重灌别的东西，权重一直在 DRAM 里，后面每次跑都跳过这一步。`--load-weights`
是不抽查直接重灌。

给这条命令设超时的话，先按当前实测的速率算出要多久：线缆速率降下来时（换个 USB 口就能差四倍）
18 分钟会变成一小时以上。

### 四、清残留

这一趟会碰到的 DRAM 区域里，输入没有覆盖到的部分要清零，共 14 MiB，25 秒。上一趟留下的残留会被
读进来影响结果。`--no-zero` 跳过。

### 五、把 prompt 喂进去

板上那份程序编好了两条路：

* **prefill** 一次处理 64 个 token，只有 prompt 正好满 64 个时才走它，一轮 1.3 秒。
* **decode** 一次处理一个 token，一步 0.5 秒。prompt 里 prefill 处理不完的那些就靠它逐个喂
  （不满 64 个的 prompt 整段都这么喂，不能补零凑数）。

prompt 加生成一共最多 128 个 token，这是这份产物的上限。

### 六、生成

每步取片上算出的那个 token，接着喂回去，直到遇到结束符或到 `--max-new`。`--show-special`
把控制 token 也打出来，`--no-stop` 遇到结束符也不停。

分词用 `data/tokenizer.json.gz` 里的词表：编码走包内的纯 Python BPE，解码按 GPT-2 的
byte-level 表还原。手上有 Qwen3-0.6B 的 GGUF 时，`--vocab <那份 gguf>` 会把编码交给
llama.cpp 的 `llama-tokenize`，两条路径在常规中英文上给出同一串 token。

## 结果不对时

| 现象 | 先看这个 |
| - | - |
| 多数趟都对，偶尔一趟从某个 token 起走偏 | 板子连续上电大半天之后会开始出零星数值错误，断电再上电就全部恢复逐字相同。先看板子上电多久了，不要急着怪到精度或者主机那一侧 |
| 生成的第一个 token 就不对 | 权重没灌对：跑 `--check-only`，抽查不过就整份重灌 |
| 每一步都超时 | 多半没烧 bitstream，或者烧错了那一份；`-v` 看每轮的状态快照 |
| 灌权重特别慢（0.16 MB/s 这个量级） | 线缆的位槽速率降了一档，换一个 USB 口。判线缆好坏看写速率和 IDCODE，不要看 `cpld` 版本号（这条线缆一直报 `0xfffe`） |
| 命令卡住不动 | 别按第二次 Ctrl-C。第一次只是让它跑完当前这步就停，硬打断正在用 JTAG 的进程会把线缆卡在写得进、读不出的状态，只能把线缆拔下来重插 |

`--dry-run` 只分词、只算计划，不碰板子，用来把主机侧和板子问题分开。
