#### 端侧推理需要专用芯片

1. 端侧推理市场庞大且分散
   1. 手机、AI PC、汽车之外，智能穿戴、安防、AIoT、具身智能等场景的需求还没有被很好地满足
   2. 这些场景的任务更集中，对面积、功耗、成本和模型能力的要求差异很大，通用推理芯片很难同时满足
   3. 以智能穿戴为例
      1. 受面积和功耗限制，芯片无法离线运行较大的模型，只能把任务交给云端
      2. 云端往返带来延迟，也受网络状况影响
      3. 实时语音、实时翻译这类场景必须在本地处理
   4. 本地推理让用户不必关心模型跑在哪里、要不要联网、数据会不会被记录
2. 定制芯片过去没有成为主流
   1. 出货量最大的手机、AI PC 是多功能设备，需要芯片足够灵活
   2. 芯片设计和制造成本极高，理性选择是做一款覆盖尽量多客户的通用产品
   3. 定制化先发生在利润更高的云端，例如 Etched、Taalas，以及 Google、Meta 的自研芯片
   4. 端侧很多场景缺少合适的芯片，应用起不来；应用起不来，芯片厂商更不愿意为这些场景专门开发芯片

#### 综合全栈设计能力

1. 利用算法余量优化硬件设计
2. 实现通用加速芯片无法达到的优化
   1. 稀疏、压缩等
3. 通过硬件特殊设计提升整体性能与效率
   1. 深度融合量化、稀疏化与数据压缩等硬件协同能力
   2. 专门设计针对固定权重的专有解压缩指令集
4. 编译器和硬件电路的精密协作
   1. 最大化软件静态调度
   2. 最简化硬件的逻辑功能
5. 针对端侧推理的微架构优化
   1. 指令设计
   2. Launch 流程和控制
6. 模型固化后，软件栈大幅简化
   1. 编译器、算子、框架、固件和运行时这一整套软件层，复杂度随模型固化大幅下降
   2. 客户拿到的芯片接近开箱即用，省去软件栈的开发和维护投入

#### 最适合端侧推理的存储方案

1. 成本
   1. DRAM/SRAM 本身硬件成本居高不下
   2. DRAM/SRAM 还需要额外搭配 NAND 进行权重的非易失性存储
   3. 为提高快速响应能力，采用高速 NAND 方案及配套控制 CPU 也是一笔不小的成本
2. 带宽与功耗
   1. 所有需要跨 Die 通讯的存储方案，即便采用 NAND 存储，要达到一定的带宽，必然伴随很高功耗，这也是存储墙的核心体现之一
   2. 存算一体（Die 内存储）面临存储器与逻辑工艺不兼容的问题，综合成本难以达到理想状态
   3. SRAM 虽然能克服上述问题且带宽可以做到很大，但面积效率在所有存储方案中最低，明显不适合敏感的端侧场景
   4. 在以上看似没有最合适端侧存储方案的情况下，如果牺牲可擦除特性，即采用 ROM，将是最理想的端侧权重存储方案
      1. 云端已有先例：Taalas HC1 把 Llama 3.1 8B 的权重直接做进晶体管（TSMC 6nm），单用户约 17000 token/s，NVIDIA H200 运行同一模型约 230 token/s（<https://www.cnx-software.com/2026/02/22/taalas-hc1-hardwired-llama-3-1-8b-ai-accelerator-delivers-up-to-17000-tokens-s/>）
3. ROM
   1. 当前的通用高密度ROM IP的密度也没有达到一个非常理想的性价比
   2. 需要进行全新的适合存储LLM权重的设计
      1. 不仅仅是提高密度，可以进行对应的压缩
      2. 降低容错能力提高密度
      3. 探索无晶体管，纯导线的ROM实现方案
4. 如何克服权重不能修改带来的问题？
   1. 支持高效微调
      1. 可以通过外置 LoRA 参数来微调权重，支持仅部分参数可变的芯片（ROM + LoRA）
      2. Kernel 和微调参数可以动态加载进行微调
      3. 仅微调 0.01% 参数就能取得不错的效果（BEFT），例如 7 GB 权重仅需 7GB / 10000 = 700KB微调参数
   2. 将灵活性转移到推理阶段，通过上下文注入实现通用模型对不同应用的适配
   3. 通用大模型的不同版本仅存在性能差异，没有本质功能差异，可以通过提示词实现不同的功能
   4. 能力退化的旧款芯片可以通过降级部署，满足较低需求的场景
   5. 大模型应用未来将配合 Agent 逐步产品化、服务化，不再过度关注底层基础模型

#### AI-Native 的开发流程，需要全流程的 Agent 脚手架

**LLM AI 擅长在一个明确、可验证的需求与任务前提下寻找可行解**

1. 针对加速芯片的开发，从算法到电路版图（GDS）存在非常长的技术栈和方法论。
2. AI 虽然能够理解整个开发过程，但如果直接面对端到端的任务目标和验证工具，LLM 只能根据概率输出一个可行、但绝对称不上合理的结果。特别是整个加速芯片从算法到软件再到硬件电路，是一个极其庞大的工程。
3. 我们的解决办法是：利用已经非常成熟的工程开发流程，把整个技术链条进行分层解耦。每个层级都配备对应的“仿真环境”和验证工具，让当前的 LLM 具备稳健的逐步推进与自我验证能力。
4. 本质上，人类的分工经验也同样适合于 Agent。下面这些工具，是在芯片开发过程中长期经验积累沉淀下来的成熟、可靠工具，是 **AI-Native 的核心资产**：
   1. **Fuse**：一个高度灵活的编译器基础工具，用最直观的逻辑编译算法的计算需求
   2. **Logix**：硬件架构/微架构仿真器，充当软硬件设计的直接桥梁
   3. **Pyrilog**：高层次物理电路语言和编译器，通过定制 DSL，赋予 LLM 使用物理资源的手感与感知
5. 芯片设计不再是传统繁重的开发流程，而是转变为输入算法需求、输出芯片电路的一个能够自动迭代和优化的整体流水线。
6. AI-Native 的芯片开发流程不仅在于提升最终 PPA，研发效率的飞跃对整个芯片生命周期和商业化价值至关重要：
   1. 全新需求的开发周期可以控制在 3 个月以内
7. 芯片设计几乎没有容错空间，首先要保证不出错，因此人和 AI 分工明确：
   1. AI 承担繁琐、重复的工作，以及大规模的设计空间探索和结果收敛
   2. 人制定目标、约束和边界，引导 AI 有针对性地探索
   3. 人在关键节点验收 AI 的结果

#### 流片和验证

1. 对应的工具和流程都是经过多代芯片实际流片验证过的精华。
   1. 很多约束和判断无法只从论文、benchmark 或仿真中获得，必须靠真实硅片的反馈积累。
   2. 先有真实的流片经验，再把经验编码进 Agent。
2. 架构效率最终体现在优秀的芯片综合 PPA：
   1. 单芯片上运行完整推理（包含 Input Token、Output Token、所有算子、底层软件与 Runtime 程序），编译后仅有 56 KB 大小。
   2. 整个推理过程只需要一个片上 RV32IM CPU 软核作为控制调度，其余全为静态电路。
   3. 在 FPGA（XC7K480T）上即可跑通 Qwen3 0.6B，速度达到 15.45 token/s（@101MHz，1024 上下文长度，Q8 量化）。
